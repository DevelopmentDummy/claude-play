# 앱 모드 플랫폼 확장 — 설계

> 상태: 설계 승인됨 (2026-09-12). 구현 계획 미작성.
> 범위: **플랫폼 확장만.** 실제 게임/월드 콘텐츠는 별도 사이클.

## 1. 문제

지금의 페르소나는 **중앙 채팅 스트림 + 주변 Handlebars 패널**이라는 셸을 무조건 전제한다. 메인 플레이 루프가 유저↔AI 대화 턴인 경우에는 잘 맞지만, 다음과 같은 것은 만들 수 없다:

- 메인 조작이 **전용 UI에서의 게임식 조작**이고 대화는 보조이거나 없는 것
- 유저 캐릭터 외의 개체들이 **각자 자기 턴을 지속적으로 돌면서** 월드 규칙 안에서 행동하는 것
- 월드 관리자·이벤트 디렉터처럼 **캐릭터를 연기하지 않는** 기능성 AI 스레드가 배경에서 도는 것

이 문서는 그런 것들을 만들 수 있게 하는 **플랫폼 확장**을 설계한다. 특정 게임(림월드/스타듀 밸리 류)은 검증용 예시일 뿐 목표가 아니다.

## 2. 승인된 범위 결정

| 결정 | 선택 | 근거 |
|---|---|---|
| 메인 에이전트 | **조용한 코디네이터** (살아있되 자동 발화 없음) | 완전 비활성은 이벤트 큐·메모·style-check·`report_to_main`의 흡수처를 전부 재배선해야 함. v2로 미룸 |
| 화면 자유도 | **앱 슬롯**을 기존 패널 시스템 위에 얹음 | 게임 UI에 필요한 자유도를 얻으면서 패널 엔진·액션·모달 배관을 그대로 재사용 |
| 스레드 구동 | **병렬 독립 루프 + 의도 큐** | "각자 자기 턴을 지속적으로" 요구에 맞는 유일한 모델. 느린 스레드가 세계를 멈추지 않음 |
| v1 결과물 | **플랫폼 확장 + 스텁 앱 검증** | 계약이 안 굳은 상태에서 레퍼런스 게임을 같이 만들면 둘 다 흔들림 |
| 스레드 작업 공간 | **공유 cwd + 스레드별 사설 디렉토리** | 런타임 스폰과 궁합. 역할별 도구 분리는 디렉토리 복제가 아니라 도구 레벨 게이트로 |

## 3. 아키텍처 개요

```
   앱 슬롯 (shadow DOM, 1회 마운트)
        │  submit(유저 조작)          ▲ stateChanged 이벤트
        ▼                              │
   ┌──────────────────────────────────────────┐
   │  월드 엔진  tools/world.js                │
   │  observe / submit / step / snapshot       │  ← 규칙이 존재하는 유일한 장소
   └──────────────────────────────────────────┘
        ▲  submit(의도)      │ observe(관측)
        │                    ▼
   스레드 루프 런타임 ── 스레드 N개 (역할 템플릿 × params)
        │
        └─ 에스컬레이션 시에만 → 메인 에이전트 (조용한 코디네이터)
```

핵심 불변식 세 가지:

1. **규칙은 `step()`에만 있다.** 유저 조작이든 AI 의도든 같은 큐를 통과하고 같은 검증을 받는다.
2. **진실은 `world.json`에 있다.** 대화 기록은 휘발성 작업 메모리다.
3. **관찰자는 동등하다.** 메인·스레드·앱이 같은 `observe` 계약을 쓴다. 메인은 `observerId: "main"`인 관찰자일 뿐이다.

## 4. 앱 슬롯

### 4.1 렌더 정책

`AppSlot`은 `PanelSlot`과 같은 shadow DOM 기법을 쓰되 **정책이 반대**다.

`PanelSlot`은 상태가 바뀌면 `shadow.innerHTML`을 갈아끼우고 `<script>`를 `Function()`으로 재실행한다 (`src/components/PanelSlot.tsx`). Handlebars 조각에는 맞지만 게임 캔버스에는 치명적이다 — 상태 write 한 번에 rAF 루프·캔버스 컨텍스트·이벤트 리스너가 전부 초기화된다.

따라서 `AppSlot`은:

- `app/index.html`을 shadow에 **한 번만** 주입하고 스크립트를 **한 번만** 실행한다. 이후 `shadow.innerHTML`을 절대 다시 쓰지 않는다.
- 상태 변경은 기존 `dispatchBridgeEvent` 패턴으로 `stateChanged` 이벤트를 쏜다. 앱이 받아서 자기 방식으로 갱신한다. 재렌더 없음.
- 앱 스크립트 실행을 try/catch로 감싸고 React `ErrorBoundary`를 둔다.

### 4.2 iframe을 쓰지 않는 이유

검토했으나 기각했다.

- 같은 오리진 iframe은 실질 격리를 주지 않는다. 진짜 격리를 받으려면 `sandbox="allow-scripts"`로 오리진을 opaque하게 만들어야 하고, 그러면 앱이 세션 API를 직접 호출할 수 없어 **모든 통신이 postMessage 경유**가 된다.
- 잃는 것이 크다: `layout.theme`의 CSS 변수가 프레임을 못 넘고, 모달 스택·ESC·드래그가 경계에서 끊기고, 이미지 클릭 → `ImageModal` 통합이 단절되고, 모바일 뷰포트/포커스 문제가 새로 생긴다.
- **신뢰 경계 논거가 성립하지 않는다.** 플랫폼은 지금도 패널 HTML의 `<script>`를 그대로 실행한다. 앱 코드의 출처는 동일하므로 iframe으로 새로 막히는 위험이 없다. import한 페르소나를 실행하는 시나리오에서도 위험 수준은 이미 패널과 같다.

CSS 격리는 shadow DOM이 그대로 제공하므로 실질 손실이 거의 없다. 원래 문제는 iframe이냐가 아니라 **렌더 정책**이었다.

### 4.3 브리지와 챗 강등

앱은 기존 `__panelBridge`를 확장해서 쓴다 (`updateVariables` / `updateData` / `updateLayout` / `runTool` / `sendMessage`). postMessage 계층이 없으므로 테마·모달·ImageModal 통합이 공짜로 따라온다.

`layout.chat.mode`로 챗을 강등한다:

- `"normal"` — 기존 동작 (기본값)
- `"dock"` — 앱이 메인 영역, 챗은 하단 독
- `"hidden"` — 앱이 전체, 챗 없음

`layout.app`이 없으면 전부 기존 동작이므로 **기존 페르소나는 무영향**이다.

### 4.4 정적 서빙

`src/lib/static-file.ts`의 `STATIC_MIME`에 `.js` / `.html` / `.css`가 없다 (현재 이미지·오디오·비디오만). 앱 번들 서빙을 위해 추가가 필요하다. 서빙 자체는 기존 `files/[...filepath]` 라우트를 그대로 쓴다.

## 5. 월드 엔진 계약

### 5.1 엔진은 tool 모듈이다

엔진은 페르소나의 tool 모듈 하나다 — `tools/world.js` (이름은 `layout.app.engine`으로 지정, 기본 `world`). 기존 tool 계약을 그대로 쓴다: CommonJS 함수 export, `action`으로 디스패치, `{ variables, data, result }` 반환. **새 실행 경로를 만들지 않는다.**

두 가지 기존 동작이 설계를 제약한다 (`src/app/api/sessions/[id]/tools/[name]/route.ts`):

- `require.cache`가 **매 호출 purge**된다 → 엔진은 메모리 상태를 가질 수 없다. 모든 월드 상태가 디스크에 있어야 한다.
- 라우트가 반환 패치를 `mutateSessionJson`으로 적용한다 → **엔진은 파일을 직접 쓰지 않는다.** 이게 곧 단일 writer 초크포인트다.
- 타임아웃은 10초 (`pipeline`이라는 이름만 30분). 엔진 액션은 전부 짧으므로 충분하고, 이름 분기는 건드리지 않는다.

월드 상태는 **한 파일**(`world.json`)에 모은다. `mutateSessionJson`의 `runExclusive(filePath)` 파일별 뮤텍스가 곧 월드 뮤텍스가 되도록 하기 위해서다. `variables.json`은 패널 표시용으로만 남는다.

**호출 경로와 결과 해석**: `thread-loop.ts`는 엔진을 직접 `require`하지 않고 `world-engine.ts`를 거쳐 **기존 tool 라우트로** 호출한다. 패치 적용·타임아웃·경로 안전이 전부 한 곳에 유지되기 때문이다. 라우트는 `{variables, data}` 패치만 해석하고 `result`는 호출자에게 그대로 돌려주므로:

- 월드 상태 변경(스레드의 `memory` 포함)은 **`data: { world: {...} }` 패치**다. 라우트가 적용한다.
- `result.threads: { spawn, despawn }`는 패치가 아니다. 라우트는 모르고, **`thread-loop.ts`가 반환값을 보고 해석**한다 (§6.4).

즉 "엔진은 파일을 직접 쓰지 않는다"는 월드 상태에 대한 불변식이고, 스레드 스폰/소멸은 상태가 아니라 런타임 명령이라 다른 경로를 탄다.

### 5.2 액션 4개

| action | 호출자 | 동작 | 상태 변경 |
|---|---|---|---|
| `observe(observerId, opts)` | 루프 런타임, 메인 깨어날 때 | 관찰자 시점의 브리핑을 텍스트로 반환 | 없음 |
| `submit(observerId, intent)` | 스레드(`run_tool` 경유), 앱(유저 조작) | 의도를 큐에 추가. **검증하지 않음** (§5.6 참조) | 큐만 |
| `step()` | 루프 런타임 (틱) | 큐에서 N건을 꺼내 규칙으로 검증·적용. 기각분은 사유와 함께 기록 | 있음 |
| `snapshot()` | 앱 슬롯 | 렌더용 월드 상태 | 없음 |

유저 캐릭터의 조작도 `submit`을 탄다. 유저와 스레드가 **같은 문을 통과**하므로 규칙이 한 곳에만 존재한다.

### 5.3 왜 메시지 펌프가 아니라 권위 서버인가

윈도우 메시지 펌프와 구조가 유사하다 — 출처가 무엇이든 하나의 큐에 같은 모양으로 들어가고, 소비자가 하나이며, 순서가 결정된다. 그러나 두 가지가 다르다:

1. **의도는 기각될 수 있다.** `WM_*`는 배달되면 그만이지만 `submit`된 의도는 `step`에서 월드 규칙에 비추어 기각될 수 있다. 이건 권위 서버(authoritative server) + 커맨드 큐 모델이다. 기각 사유가 해당 관찰자의 다음 `observe`에 실려 돌아가는 것이 핵심 피드백 루프다.
2. **1건씩 디스패치가 아니라 배치 드레인이다.** 같은 틱에 두 스레드가 같은 자원을 노릴 때, 1건씩이면 먼저 온 쪽이 이기고 끝이지만 배치면 엔진이 경합을 의도적으로 판정할 수 있다. 병렬 루프에서 관측 시점과 적용 시점이 어긋나는 문제를 흡수하는 자리다.

### 5.4 관측은 계층이다

`observe(observerId, opts)`가 메인·스레드·앱을 전부 담당하며 반환은 계층 구성이다:

- **월드 공통** — 시간/계절/날씨, 공개 사건, 전역 지표. 모든 관찰자가 동일
- **역할 스코프** — 역할이 선언한 `scope`에 따른 가시 범위. 관리자는 전역 집계, 행위자는 주변 반경, 디렉터는 통계만
- **관찰자 사적 상태** — `params`로 식별되는 자기 자신: 소지품·목표·관계, 그리고 월드에 저장된 자기 `memory`
- **직전 틱 피드백** — 기각된 의도와 사유

`scope` 해석은 엔진(페르소나 저자)의 몫이고 플랫폼은 값을 전달만 한다.

**`opts.since`가 토큰 비용을 지배한다.** 관측은 매 틱마다 모든 스레드에 간다.

- prime 직후: `since` 없음 → 전체 스냅샷
- 이어지는 틱: `since = 직전 관측 시각` → 변화분만

살아있는 스레드의 대화 컨텍스트가 이미 이전 관측을 담고 있으므로 델타가 정당하다. 컨텍스트 리셋 시 `since`가 초기화되면서 자연히 전체 스냅샷으로 돌아간다.

### 5.5 동시성

락이 두 층이다.

- **파일 뮤텍스** (`runExclusive(world.json)`) — `mutateSessionJson`이 이미 제공. 쓰기 순간에만 잡히고 LLM 턴 동안은 잡히지 않는다. `submit`도 이 락을 탄다.
- **세션 뮤텍스** (신규, `world-engine.ts`) — `step` 하나만 이 락 아래서 돈다.

세션 뮤텍스가 따로 필요한 이유: 엔진이 받는 `context`는 **호출 시점 스냅샷**이고 패치는 나중에 적용된다. `step` 두 개가 동시에 돌면 둘 다 옛 상태로 계산해 lost update가 난다. 파일 뮤텍스는 이걸 못 막는다 (읽기-계산-쓰기가 하나의 임계 구역이 아니므로).

`observe`/`snapshot`은 읽기 전용이고, `submit`은 §5.6의 구조 덕분에 세션 뮤텍스가 필요 없다. 직렬화 대상이 `step` 하나뿐이라 병렬성 손실이 없다.

### 5.6 의도 큐는 배열이 아니라 키 있는 객체다

**`applyPatch`는 배열을 교체한다** (`deepMerge`, `src/lib/session-state.ts`) — 병합되는 것은 plain object뿐이다. 따라서 큐를 배열로 두면 동시 `submit` 두 건이 각각 옛 스냅샷을 읽고 자기 것만 덧붙인 **전체 배열**을 반환해서 나중 것이 먼저 것을 덮어쓴다. 의도가 조용히 사라진다.

큐는 키 있는 객체다:

```jsonc
// world.json
{
  "intents": {
    "villager_03__41": { "seq": 41, "at": 1757... , "observerId": "villager_03", "intent": {...} },
    "user__12":        { "seq": 12, "at": 1757... , "observerId": "user", "intent": {...} }
  }
}
```

- `submit`은 `{ $merge: "deep", intents: { "<key>": {...} } }`를 반환한다. 형제 키가 보존되므로 **동시 제출이 안전하다** — 옛 스냅샷을 읽었어도 자기 키만 쓰기 때문에 상관없다.
- `step`은 소비한 키를 `$unset: ["intents.villager_03__41", ...]`로 제거한다 (`unsetPath`가 dot-path를 지원).
- **키에 `.`이 들어가면 안 된다** — `unsetPath`가 dot으로 분해하기 때문이다. 키 형식은 `{observerId}__{seq}`이고 `observerId`는 `[a-z0-9_-]`로 제한한다.
- **객체 키 순서에 의존하지 않는다.** 처리 순서는 각 항목의 `seq`/`at`으로 엔진이 정렬해서 결정한다.

## 6. 역할과 스레드

### 6.1 역할 ≠ 인스턴스

루프를 도는 주체가 캐릭터를 연기한다는 보장이 없다. 월드 관리자·이벤트 디렉터·경제 시뮬레이터·배경 서술자가 모두 같은 런타임을 쓴다. 따라서 용어는 **서브에이전트 스레드**다.

- **역할(role)** = 템플릿: 지침 파일 + 모델/프로바이더/effort + `scope` + 루프 설정
- **스레드(thread)** = 인스턴스: `{ threadId, role, params }`

`params`가 정체성이다 (`{ entityId: "villager_03" }`). 같은 역할에서 스레드 20개가 뜨고 지침은 한 벌이다.

현재 `SubAgentManager`는 **이름 → 인스턴스 1:1 Map**이고 `dispatch(name, ...)`가 이름으로 라우팅한다 (`src/lib/subagent-manager.ts`). 이 키가 `threadId`로 바뀐다.

### 6.2 하위호환

기존 `subagents[]` 배열의 각 항목은 "스레드 하나짜리 역할"로 승격되고 `threadId === name`이 된다. `bridge_delegate`·`report_to_main`·서브 대화 모달이 그대로 동작한다.

스레드 디렉토리는 기존 `subagents/{name}/` 경로를 그대로 쓴다 — 새 스레드는 같은 폴더 아래 새 ID로 생기므로 **마이그레이션이 없고 resume id 유실도 없다**.

### 6.3 정체성 주입

역할 지침은 공유되고, 스폰 시 선행 메시지에 `[THREAD] threadId=..., params={...}`가 붙는다. `primed = !!resumeId`이므로 (`src/lib/subagent-instance.ts`) 재개된 스레드는 이미 자기가 누군지 알고 재주입하지 않는다.

### 6.4 라이브 레지스트리

어떤 스레드가 존재하는지는 매니페스트가 아니라 `threads.json`이다. 엔진이 `result.threads: { spawn, despawn }`를 반환하면 **`thread-loop.ts`가** (tool 라우트가 아니라 — §5.1) 해석해 적용하고 `threads.json`에 기록한다. 세션 재open 시 이 파일로 복원한다. 월드에서 개체가 태어나면 스레드가 생기고 사라지면 소멸한다.

## 7. 루프 런타임

`src/lib/thread-loop.ts` (신규).

스레드별 타이머 → `observe(observerId)` → `dispatch` → 스레드가 `run_tool`로 `submit` → 턴 종료 시 런타임이 세션 뮤텍스 아래 `step()`.

스레드가 아직 바쁘면 그 틱은 **건너뛴다** (큐에 쌓지 않는다).

### 7.0 틱 순서 (고정)

`step()`은 **스레드 턴마다가 아니라 세션 틱마다 한 번** 돈다:

1. 세션 틱 시작 — 이번 틱에 깨울 스레드들을 고른다 (주기 도래 + 바쁘지 않음 + 동시 실행 예산 여유)
2. 선택된 스레드들에게 `observe` → `dispatch`. **병렬**로 진행
3. 이번 틱에 디스패치된 턴이 전부 끝날 때까지 대기 (예산 상한 초과 시 타임아웃으로 끊고 다음 틱으로 넘김)
4. 세션 뮤텍스 아래 `step()` **1회** — 이번 틱에 쌓인 의도를 한 배치로 드레인
5. 기각 결과는 각 관찰자의 다음 `observe`에 실림

**이 순서가 §5.3의 배치 경합 판정을 성립시킨다.** 턴마다 `step`을 돌리면 배치 크기가 항상 1이 되어 "같은 틱의 경합을 의도적으로 판정한다"가 공허해진다.

부작용으로 **한 틱 안의 관측 시점이 일관된다** — 같은 틱에 깨어난 스레드들은 전부 같은 월드 상태를 본다. 느린 스레드가 3단계를 지연시킬 수는 있으나, 예산 타임아웃이 있어 세계가 멈추지는 않는다 (그 스레드의 의도는 다음 틱 배치에 합류한다).

### 7.1 틱 예산

v1 필수. 없으면 스레드 N개가 24시간 CLI를 돌린다.

| 항목 | 기본값 | 이유 |
|---|---|---|
| 역할별 최소 주기 | 5초 하한 | 저자의 실수(100ms)를 막음 |
| 세션 동시 실행 턴 | 3 | 동시에 도는 CLI 프로세스의 실질 상한. 프리워밍 스왑도 이 예산에 포함 |
| 세션당 스레드 상한 | 12 (`THREAD_MAX`) | 현재 `SUBAGENT_MAX=6`을 대체 |
| 클라이언트 미접속 | 자동 일시정지 | 아무도 안 보는데 토큰을 태우지 않음 |
| 유저 일시정지/속도 | 앱 슬롯 + StatusBar | 사용자가 언제든 세계를 멈출 수 있어야 함 |

전부 설정값이며 실사용 후 조정한다.

### 7.2 컨텍스트 성장 — 상태 기반 재prime

루프 스레드는 transcript가 무한히 자란다. 메인에는 `runCompactionResumeHook`이 있지만 서브에는 없다.

**대화 요약 턴을 돌리지 않는다.** 요약 턴은 하필 컨텍스트가 가장 클 때 도는 턴이라 입력이 최대이고, 뒤이은 콜드 재prime까지 합치면 해당 스레드가 두 턴 길이만큼 얼어붙는다.

대신 권위 있는 상태가 이미 `world.json`에 있다는 점을 쓴다:

- 스레드는 자기 턴에 의도를 제출하면서 짧은 기억 갱신(`memory`)을 같이 싣고, 엔진이 월드에 쓴다.
- 리셋 = 프로세스를 버리고 새로 띄운다. **추가 LLM 호출 0회.**
- 재prime 시 **플랫폼이 조립하는 것은 역할 지침 + `[THREAD] params` 두 가지뿐이고**, 세 번째 조각인 기억은
  **엔진의 `observe`가 실어 보낸다**. 리셋 후 첫 `observe`는 `since`가 초기화되어 전체 스냅샷이므로,
  엔진이 관찰자 사적 상태(§5.4)에 그 스레드의 `memory`를 포함시키면 재prime이 완성된다.

> **책임 분담**: 플랫폼은 기억을 저장하지도 주입하지도 않는다. 기억은 월드 데이터이고 전달 경로는 `observe` 하나다.
> 따라서 **엔진 저자가 `observe`에 `memory`를 넣지 않으면 리셋된 스레드는 자기 과거를 잃는다.**
> 참조 구현(`scripts/fixtures/app-mode-stub/tools/world.js`)이 이 패턴을 보여준다.

대화의 뉘앙스 자체가 가치인 역할은 역할 설정에서 요약 턴 방식을 **옵트인**으로 고를 수 있다.

남는 지연은 프로세스 스폰(윈도우 CLI 콜드 스타트, 초 단위)이다. 두 가지로 덮는다:

1. **프리워밍 스왑** — 교체 프로세스를 먼저 띄워 prime까지 끝낸 뒤 옛 프로세스를 죽이고 갈아끼운다. 중단이 사실상 0. 동시 실행 예산 하나를 잠시 더 먹는다.
2. **지터** — 리셋 주기 K를 스레드마다 ±20% 흔든다. 안 그러면 같은 역할 스레드들이 같은 틱에 동시 리셋되어 세계가 한 번에 멈춘다.

리셋은 **틱 경계에서만** 일어난다 — 의도 제출 직후, `step` 적용 **후**.

## 8. 조용한 코디네이터

### 8.1 대부분 공짜다

실측 결과:

- `report_to_main`은 서브 transcript에 기록만 하고 메인 턴을 강제하지 않는다. 스레드 12개가 계속 보고해도 메인은 깨지 않는다.
- `runStyleCheckHook` / `runSessionMemoTick`은 `processResult` 안에서 **메인 턴이 끝난 직후에만** 호출된다 (`src/lib/session-instance.ts`). 메인 턴이 없으면 그냥 안 돈다. 오작동하지 않는다.
- `autoTrigger: "onAssistantTurn"` 스레드도 메인 턴이 없으면 자연히 안 뛴다.

### 8.2 메인을 깨우는 조건

세 가지뿐이다: ① 유저가 직접 메시지를 보냄 ② 명시적 에스컬레이션(엔진이나 스레드가 `fire_ai` autoResume 호출) ③ 유저가 챗을 열고 말을 검.

스레드의 일상 보고는 절대 깨우지 않는다. 이건 코드 변경이 거의 없고 **역할 지침과 MCP 도구 설명에 적어야 하는 계약**이다.

**클라이언트 미접속 중의 에스컬레이션**: 루프는 §7.1에 따라 자동 일시정지되므로 스레드발 에스컬레이션은 애초에 발생하지 않는다. 일시정지 직전에 이미 떠 있던 `fire_ai`가 완료되는 경우는 기존 disk-first fallback 경로를 그대로 탄다 — 결과가 디스크에 남고, 유저가 돌아와 접속하면 그때 전달된다. 즉 **새 배관이 필요 없고, 이벤트 큐도 쓰지 않는다**.

### 8.3 앱 모드에서는 이벤트 큐를 쓰지 않는다

이벤트 큐의 존재 이유는 "메인이 다음 턴에 알아야 할 델타를 모아둔다"인데, 앱 모드에서는 두 전제가 깨진다 — 다음 턴이 언제인지 모르고, 진실은 이미 `world.json`에 현재 상태로 있다. 델타 로그는 서로 상쇄되기까지 한다("밀 +3", "밀 -2"를 재생하느니 "밀 1"을 읽는 게 정확하고 싸다).

따라서:

- **엔진과 스레드는 `queueEvent`를 쓰지 않는다.** 월드에 일어난 일은 월드에 기록되고 그게 유일한 채널이다.
- **메인이 깨어날 때는 재생이 아니라 브리핑을 받는다.** 런타임이 `observe("main")`을 한 번 호출해 현재 월드 상태 요약을 시스템 헤더로 붙인다.

이것이 §5.4와 구조적으로 일관된다 — 메인은 `role: "main"`인 또 하나의 관찰자이고, 컨텍스트 리셋 시 스레드를 상태로부터 재prime하는 것과 같은 메커니즘이다. **메커니즘이 하나 줄어든다.**

이벤트 큐 상한은 두지 않는다. 앱 모드가 큐를 안 쓰면 무한 성장이 사라지고, 일반 모드는 매 턴 flush되므로 애초에 문제가 없었다. 큐는 드문 시스템 이벤트(재시작 마커 등)에만 지금 그대로 남는다. `session-instance.ts`의 큐 코드는 **무변경**이다.

### 8.4 로비 카드 메모

세션 메모는 턴 구동이라 앱 모드에서 갱신되지 않는다. 엔진이 기존 `bridge_set_session_memo`를 호출해 "3일차, 마을 인구 7"처럼 직접 채운다. 신규 배관 없음.

## 9. 단일 writer 강제

실제 구멍은 앱 브리지다. `__panelBridge.updateData(fileName, patch)`는 `PROTECTED_FILES`만 아니면 세션의 아무 `.json`이나 쓴다 — `world.json`도 포함이다. 이러면 앱이 `submit`을 우회해 월드를 직접 고칠 수 있고 §5의 불변식이 깨진다.

엔진의 월드 쓰기와 앱의 쓰기가 **서로 다른 라우트**를 타므로 분리가 깔끔하다:

| 경로 | 월드 파일 쓰기 |
|---|---|
| tool 라우트 (엔진 반환 패치) | 허용 |
| `/api/sessions/[id]/variables` PATCH (앱·패널) | **거부** |

즉 variables 라우트에만 "앱 모드에서 `layout.app.worldFile`은 쓰기 금지"를 추가한다. 엔진은 영향 없고, 앱은 `runTool("world", { action: "submit" })`로 가야만 한다.

**tool 라우트의 `PROTECTED_FILES`에는 `world.json`을 넣지 않는다.** 넣으면 엔진 자신의 월드 쓰기가 막혀 설계가 통째로 깨진다. 보호는 variables 라우트 쪽 한 곳에만 존재한다.

- 관측 계약 — `since` 유무에 따른 전체/델타 분기

### 12.2 스텁 앱 라이브 스모크

타일 없는 텍스트 월드, 역할 2개(관리자 1 + 행위자 2), 규칙 하나(자원 집기, 경합 시 기각).

확인 항목:

- [ ] 스레드가 뜨고 틱을 돌고 의도가 적용되는가
- [ ] 기각 사유가 다음 관측에 실리는가
- [ ] 일시정지가 먹는가
- [ ] 클라이언트를 끊으면 멈추는가
- [ ] 컨텍스트 리셋 후 정체성이 유지되는가 (프리워밍 스왑 포함)
- [ ] 세션 재open 후 스레드가 복원되는가
- [ ] 앱이 `variables` 라우트로 월드 파일을 못 쓰는가
- [ ] 바쁜 스레드를 despawn했을 때 프로세스가 실제로 죽고 `subagent-procs.json`에 고아 PID가 남지 않는가
- [ ] 동시 `submit` 2건이 둘 다 큐에 남는가 (§5.6 lost-write 회귀)
- [ ] 기존 페르소나(앱 모드 아님)가 무영향인가

### 12.3 등급과 전파

검증 등급은 **hot-path**다 (세션 런타임 + 프로바이더 spawn). typecheck로 끝나지 않는다. 라이브 스모크를 못 돌리면 커밋 메시지에 명기하고 `HANDOVER.md` §4에 등재한다.

문서 전파: `npm run check:docs`가 신규 `src/lib/*`와 신규 컴포넌트의 문서 행을 강제한다. `codebase-map.md`에 "앱 모드 / 월드 / 스레드 루프" 행을 추가하고 `architecture.md`·`data-model.md`·`frontend.md`·`session-lifecycle.md`·`change-propagation.md`를 갱신한다.

## 13. 명시적 비범위 (v2 이후)

- **메인 에이전트 완전 비활성** — 이벤트 큐·메모·style-check·`report_to_main` 흡수처 재배선 필요
- **빌더의 앱 페르소나 저작 전용 UI/위저드** — 폼 기반 저작 흐름. v1에서는 **빌더 AI가 지침으로 저작**한다:
  `app-spec.md`(저작 계약)가 빌더 디렉토리로 복사되고, `builder-prompt.md`에 "앱 모드" 절이 있으며,
  `bridge_define_role` MCP 도구가 v2 매니페스트(역할+스레드)를 검증된 경로로 쓴다. 엔진·앱 HTML은 빌더가 직접 쓴다.
  더불어 다음 가드레일이 있다: `builder-prompt.md`가 (a) `layout.json`의 `app`/`chat.mode`를 지우지 말 것,
  (b) `subagents.json`의 `roles`/`threads`를 직접 쓰지 말 것(도구는 보존함), (c) 상한은 `subagents[]`+`threads[]`
  합계라는 것을 지시하고, `bridge_define_subagent`는 합계 기준으로 상한을 검사한다 —
  넘기면 파서가 throw하고 `spawnAll`이 bail해서 그 세션의 서브·스레드가 **전부** 안 뜨기 때문.
- **레퍼런스 게임** — 타일맵·경제·상호작용을 갖춘 실제 월드. 자체 spec → plan 사이클
- **역할별 도구 격리** — 필요해지면 디렉토리 복제가 아니라 MCP 도구 레벨 게이트로
- **이벤트 구동 틱** — "변화가 생기면 다음 틱을 앞당긴다". 루프 위에 나중에 얹을 수 있음
